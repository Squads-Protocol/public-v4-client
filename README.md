# Squads Public Client v4

This repository hosts the code for a simplified client application for the Squads V4 Program. The app can be built, verified for integrity, and deployed as a static site using multiple hosting options, including self-hostable solutions like Docker with Nginx. Here’s how you can use it effectively.

---

## Features

- **Verifiable Build**: The `dist/` directory contains the static files that can be verified via a hash. This ensures the integrity of the build delivered.
    - Verification can be done against:
        - **Remote URLs**: Downloaded files can be verified for consistency with the expected hash.
        - **IPFS CID**: Retrieve the build from IPFS and verify its authenticity.
- **Self-hosting**: Run the application as a Docker container using an Nginx server for fully self-managed hosting.
- **Validator management**: Manage vote accounts and stake accounts that a vault controls, with no Squads service in the path. See [Validator Management](#validator-management).
- **Readable proposals**: Vote, Stake, System, BPF Upgradeable Loader, Compute Budget and Memo instructions are decoded before you approve. A warning shows when a proposal moves a withdrawer, staker or upgrade authority away from the vaults of the multisig.

## Getting Started

The following steps will guide you to build, verify, and host the application.

### 1. **Build the Web App**

#### Prerequisites:
- [Node.js v24+](https://nodejs.org/)
- [Yarn](https://yarnpkg.com/)

#### Steps:
1. Clone the repository:
   ```bash
   git clone https://github.com/Squads-Protocol/public-v4-client
   cd public-v4-client
   ```

2. Install dependencies:
   ```bash
   yarn install --frozen-lockfile
   ```

3. Build the application:
   ```bash
   yarn build
   ```
   A `dist/` directory will be created containing the static files.


4. Generate a hash of the build:
   ```bash
   ./scripts/generate-hash.sh
   ```
---

### 2. **Verify the Build**

#### Verifying Against a Remote URL
To verify the files hosted at a remote URL:
1. Use the `scripts/verify-remote.sh` script:
   ```bash
   ./scripts/verify-remote.sh <REMOTE_URL> <EXPECTED_HASH>
   ```
   Replace `<REMOTE_URL>` with the base URL of the remote site and `<EXPECTED_HASH>` with the known SHA-256 hash of the build.

---

#### Verifying Against an IPFS CID
To verify an IPFS-hosted build:
1. Ensure you have the IPFS CLI installed (`ipfs`).
2. Use the `scripts/verify-ipfs.sh` script:
   ```bash
   ./scripts/verify-ipfs.sh <IPFS_CID> <EXPECTED_HASH>
   ```
   Replace `<IPFS_CID>` with the CID of the IPFS build and `<EXPECTED_HASH>` with the known SHA-256 hash.

---

### 3. **Self-Host with Docker**

#### Prerequisites:
- [Docker](https://www.docker.com/)

#### Run the Docker Container
You can deploy the web app via a self-hosted Docker container using Nginx:
1. Build the Docker image:
   ```bash
   docker build -t squads-public-v4-client .
   ```

2. Run the container:
   ```bash
   docker run -d -p 8080:80 squads-public-v4-client
   ```

The app will now be available at `http://localhost:8080`.

3. Retrieve the hash from the running container:
    ```bash
    docker exec <container_id> cat /var/build-metadata/hash.txt
    ```
---

### 4. **Build Hash**

A SHA-256 build hash is generated by combining all files in the `dist/` directory in a deterministic order.

#### To Check or Compute the Build Hash Locally:
1. Run the `scripts/generate-hash.sh` script:
   ```bash
   ./scripts/generate-hash.sh
   ```

   The output will show the computed hash of the local `dist/` content. This hash should match the one provided in the deployment.

## Validator Management

The **Validators** page manages Solana vote accounts and stake accounts that a vault of your multisig controls. All data comes from the RPC that you set on the **Settings** page. The page does not call a Squads API or a third-party API.

In the usual setup, a vault is the **authorized withdrawer** (Vote program role) of the vote account, and the **staker** and **withdrawer** (Stake program roles) of the stake accounts. The validator identity key and the authorized voter key stay on the validator.

### Supported operations

Each operation creates one vault transaction and its proposal.

| Account | Operation | Instruction |
|---|---|---|
| Vote account | Withdraw (amount, or full balance to close) | Vote `Withdraw` |
| Vote account | Change commission (whole percent) | Vote `UpdateCommission` |
| Vote account | Change commission (basis points), when the feature is active | Vote `UpdateCommissionBps` |
| Vote account | Change inflation rewards collector / block revenue collector | Vote `UpdateCommissionCollector` |
| Vote account | Change authorized withdrawer | Vote `Authorize` (Withdrawer) |
| Vote account | Change authorized voter, only for vote accounts without a BLS key | Vote `Authorize` (Voter) |
| Stake account | Create (and delegate) | System `CreateAccount` + Stake `Initialize` (+ `DelegateStake`) |
| Stake account | Delegate, Deactivate | Stake `DelegateStake`, `Deactivate` |
| Stake account | Withdraw | Stake `Withdraw` |
| Stake account | Split | System `CreateAccount` + Stake `Split` |
| Stake account | Merge | Stake `Merge` |
| Stake account | Change staker / withdrawer | Stake `Authorize` |

Before each proposal, the page:

1. Reads the account again and makes sure that the vault is the required authority.
2. Shows the decoded instructions that the vault will sign.
3. Simulates the instructions as the vault and shows the result.
4. Asks you to type `CONFIRM` when an instruction moves control away from the vaults of the multisig, or closes the vote account.

A new stake account (create or split) uses an address that the Squads program signs for at execution. You do not need an extra keypair.

### Not supported in the browser

- **Change the validator identity** (`UpdateValidatorIdentity`): the new identity key must also sign at execution.
- **Change the authorized voter of a vote account with a BLS key**: the instruction must include a BLS proof of possession that only the new voter key can make.
- **Stake lockup and custodian changes.** The page decodes them in proposals, but it does not create them.

Use the Solana CLI or the Squads CLI for these operations.

### Runbook

**Step 1. Give control to the vault (one time).** Copy the vault address from the **Validators** page (it is the same as on the Home page for the selected vault index).

- For an existing vote account, run this with the current withdrawer keypair:

  ```bash
  solana vote-authorize-withdrawer <VOTE_ACCOUNT> <CURRENT_WITHDRAWER_KEYPAIR> <VAULT_ADDRESS>
  ```

- For a new vote account, set the vault as withdrawer when you create it:

  ```bash
  solana create-vote-account <VOTE_KEYPAIR> <IDENTITY_KEYPAIR> <VAULT_ADDRESS> --commission <PERCENT>
  ```

- For an existing stake account, run this with the current authorities:

  ```bash
  solana stake-authorize <STAKE_ACCOUNT> \
    --stake-authority <CURRENT_STAKER_KEYPAIR> --new-stake-authority <VAULT_ADDRESS> \
    --withdraw-authority <CURRENT_WITHDRAWER_KEYPAIR> --new-withdraw-authority <VAULT_ADDRESS>
  ```

**Step 2. Add the vote account.** On the **Validators** page, paste the vote account address and click **Add**. You can also click **Find** to search for vote accounts whose withdrawer is the selected vault. Many public RPCs refuse this search. If the search fails, add the address by hand.

**Step 3. Propose an operation.** Click an action, fill in the form, click **Preview**, read the decoded instructions and the simulation result, then click **Propose**.

**Step 4. Approve and execute.** The other members open the **Transactions** page. Each proposal shows its decoded instructions. Members approve, and then one member executes.

> **RPC requirement.** The stake account list uses `getProgramAccounts` on the Stake program, filtered by the vault address. Use an RPC that allows this call.
